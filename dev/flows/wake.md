# /dev wake <routine> <dir> — a routine's run

The prompt a routine's trigger carries at its source is this one command and nothing else, `<dir>` being the product directory's absolute path in the runner environment. Every rule the run follows lives here, in the skill and on the board, so changing how scheduled runs behave never means editing a trigger. Work from `<dir>` for the whole run — every `TASKS` call and every task run under it — so a session that starts elsewhere (at a repo root, in an environment holding several repos) still reaches the right board. A `<dir>` that does not exist stops the run before step 1: report it, since the environment no longer matches what the routine was set up with (`flows/schedule.md` step 3). A prompt with no `<dir>` (a trigger set up before it was part of the prompt) works from where the session started.

1. **Skill check.** `SKILL_CMD check` (SKILL.md *Skill check*): show any line it prints, never stop on it.
2. **Gate.** `TASKS whoami` — an error (no readable login, or one not on the roster) stops the run; report it verbatim, since joining a board is a human step. Then `TASKS routine wake <routine>`. Exit 2 → report its reason and stop: nothing runs, and step 5 is skipped (on a one-time routine, add that the trigger is now spent and needs moving at its source once the routine is back). Otherwise `TASKS routine show <routine>` for its mode and schedule.
3. **Run its due tasks**, in the order the wake printed them. The `skipped, waiting on a decision:` and `skipped, in flight:` lines are reported, never run: a decision is the user's to give (`/dev review <id>`), and an in-flight run is someone's to finish.
   - **Attended** (the routine holds one task): `/dev <id>` as *A scheduled sitting* (`flows/lead.md`) — or, for a recurring audit, `flows/audit.md` with its scope, as *Next* routes one.
   - **Unattended**: each as `/dev <id> unattended` (`flows/unattended.md`), one after another in this session — a recurring audit through that file's audit bullet. Each is its own run: a task that file skips or stops on is reported and the next one runs, unless its gate stopped the whole session.
   - **A harness refusal** — a call refused, or held at a permission prompt — is noted where it happens: `TASKS note <id> --at "<step>" "harness refused <call>"`. The setup fixes it (`flows/schedule.md` step 7).
4. **Provenance.** Every record the run writes — the shipped record, a parked `Question:` — ends `(<mode>, <model-id>, routine <routine>)`, e.g. `(unattended, claude-opus-5-5, routine nightly)`. The unattended `(unattended, <model-id>)` is its prefix, and a run no routine started carries no tail. An attended sitting passes the tag to its implementer for the shipped record.
5. **Re-point a one-time trigger.** Only when the routine's schedule is one fire time (a timestamp): the trigger is spent once it fires, so the routine fires again only if this run moves it. Do it on every wake that passed the gate, whatever ran, a wake with nothing due included.
   - **When**: the earliest next due among the routine's tasks (`TASKS recur list`). A task not re-armed yet — still in flight (a dev run re-arms at land, not at ship) or waiting on a decision — counts as if it ran now: its cadence from today, or its schedule's next time after the one a run recorded now would cover (*Recurring*: inside a time's early window, that is the time after it — so an early wake never re-points to the time it is serving).
   - **Move it** at its source when the harness lets this session (the routine's body says how), then mirror it on the board: `TASKS routine update <routine> --schedule <timestamp>`. Never the board alone — it mirrors the source.
   - **Cannot** → notify the user with the time to set and the routine's body, and leave the board's schedule as it is. The not-started warning only shows once that time has passed, too late to save a spent trigger.
6. **Report.** One line per task (what its run reports), the skipped lines, the re-point (moved to when, or the user notified), and any harness refusal noted. The notification rules of the flow each task ran under hold: an unattended session sends one notification at most, and an attended sitting has already reached the user if it needed them.
