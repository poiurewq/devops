# Unattended — a dev run with nobody there

Read when the invocation ends in the word `unattended`: `/dev <id[, id…]> unattended`, `/dev next unattended`, or an unattended routine's wake, which passes the word the same way. Unattended is chosen, never inferred: without the word, a run is attended, whoever started it. It is for cron/scheduled or parallel agent sessions with no human present. One run = at most one shipped implementation (plus any proposals filed along the way), or one due recurring audit in its place — an audit files proposals and ships nothing. Several ids run one after another, each its own run. Multiple runs may go concurrently against the same board — the claim step is the mutex.

An unattended run does not go through the lead (`flows/lead.md`): nobody is there to stand in for, and it has no reviewer pass. It follows `flows/implement.md` with the overrides below and stops at `draft`.

**Identity**: the run acts as the human who owns this machine's GitHub account, so every piece of its work traces to a responsible person. `TASKS whoami` prints the roster handle the current GitHub login holds — call it `<owner>` and pass it explicitly as `--assignee`. If it errors (gh unreadable, or the login is not on the roster), stop and report that: joining a board is a human step (`/dev init`), and an unattended run never registers a contributor. Which agent did the work is **provenance**, not identity: end every shipped record with `(unattended, <model-id>)` — `(unattended, <model-id>, routine <name>)` when a routine's wake started the run (`flows/wake.md`); ship mirrors it onto the PR body — so reviewers can tell agent work from the owner's own. Run from the product directory or pass `--scope`.

**Hard limits**: never merge or approve a PR, mark a draft PR ready for review (or un-ready one), resolve a `needs: decision` fork, flip `proposed` to `backlog` (an audit's own findings included), mark a task `not-planned`, `later` or `shelved`, delete one, file a recurring task or offer to schedule one, or otherwise decide for the human — a pointless-looking task gets `needs: decision` with your reasoning instead. An unattended run files work and questions; humans dispose of them via flows/review.md. Never park, discard, or reset the local integration branch — that is human-only (flows/implement.md preflight).

## Nobody there: what a run never takes

These apply to a named id as much as to one `/dev next unattended` selects. A named task they exclude is reported and left alone (an untagged one gets its fork filed, below); `next unattended` skips it and selects again.

- **A `kind: umbrella` task** — all-deps-done describes exactly the umbrella that is ready for its verification pass, and that pass is a human judgment (SKILL.md *Umbrella close*; `claim` refuses one outright).
- **A `type: ops` task** — it is run, not built: `/ops run <id> unattended` is its unattended path. There is no branch to claim (`claim` refuses one).
- **A dev task whose flow waits on a human** — read the flow a task names (`TASKS flow show <name>`, and each flow in its `uses`): any `[user]` or `[confirm]` step, or an outward or hard-to-undo step implement would gate anyway (flows/implement.md *Following a flow*), needs someone to act or say `go`, and nobody will — the run would build up to that step only to discard the branch at the fork. An `[external]` step excludes it too: the work would stop at `TASKS wait` for a third party's reply, and the run never comes back to pick it up.
- **Area grounds** (`TASKS collisions <id>` / SKILL.md *Area stewardship*): exit 2 **or 3** → skip, surface the output (any assignee's `doing`, `draft`, or `review`, including the owner's other work). Exit 3 (every blocker's PR already out) offers interactive implement a proceed/stack/wait choice — that is a human call, so an unattended run skips it like any other collision and never stacks. Never pass several candidates as one collisions set — that would treat them as batch peers. Never an `all` task (those wait for a human-supervised quiet board).
- **Untagged**: do not claim and do not invent a placeholder. Recommend a reuse from `TASKS area list` or a new name to `area set`, write the fork (options + recommendation) into the body, and flag `needs: decision` — do not `area set` or `--area` until a human decides via review. **Area sanity**: a mis-tag (replace with same-width or narrower) — fix it and note why (`TASKS update <id> --area "<better>" --append "<why>"`). Adding coverage is the leaving-areas fork: do not `--area` or `area set`; write the file(s) and recommended area(s) into the body, flag `needs: decision`, move on.
- **Fork risk**: read the task body and skim the code it touches; prefer tasks that are mechanical or fully pinned down (clear scope, `Decision:` lines already present, established patterns). Don't force a risky task.

## The run

1. **Gate**: `TASKS whoami` must print `<owner>` (Identity above), else stop and report. Then `TASKS preflight` (check only — never `--park` / `--discard`). An `error:` (gh not signed in, among others): exit reporting it verbatim. Exit 2 (in-scope ahead): **stop** — report the script output and that a human must park-as-PR or discard via interactive implement; do not claim a task. Exit 0 with out-of-scope-only ahead → soft note in the report, continue.
2. **The task**: the named id, or what `/dev next unattended` selects (below). Check it against *Nobody there* above.
3. **Claim**: `TASKS claim <id> --assignee <owner> --unattended <model-id>`. `--unattended` marks the task as this run's while it is `doing` (`unattended:<model-id>` on the board and in `/dev status`), so the owner can tell it from their own work and cannot resume into the worktree you are using; leaving `doing` — ship to draft, or a fork un-claim — clears it. If the script errors (e.g. a concurrent claim race on board push), resync; under `next unattended`, select again. Use the printed `product` dir (workdir is the git worktree root).
4. **Triage scope** (flows/implement.md step 1, including its one-layer-at-a-time rule — mid-sized subtasks are fine): if oversized, file the subtasks as proposals rather than adding them live — check `TASKS related "<title>"` first and skip ones the board already has, then `TASKS add ... --status proposed`, each body noting "decomposes T<id>: <why>". Then convert the original into an umbrella and un-claim it: `TASKS update <id> --kind umbrella --deps <new-ids> --status backlog --assignee "" --branch "" --append "Decomposed into proposed T<ids>;"`. Under `next unattended`, return to selection (at most once per run); a named id stops here.
5. **Implement** per flows/implement.md steps 3–6, with one difference — **fork handling**: on hitting a genuine design fork, do not pick. Write the fork into the task body (question, options, your recommendation), then flag and un-claim: `TASKS update <id> --needs decision --status backlog --assignee "" --branch "" --append "<the fork write-up>"`, discard the branch, and stop (under `next unattended`, return to selection). Only flag *genuine* forks — choices repo conventions already settle don't count. A flow checkpoint is such a fork: nobody can say `go`. Leaving the stated areas (flows/implement.md) is a fork: do not `--area` or `area set`. Write the file(s) and recommended area(s) into the body, then flag and un-claim as above. A `Decision:` already on the body for this widen is prior approval — retry apply+collisions; do not file a second fork. (Local-ahead was already cleared or soft-noted in step 1 — do not re-triage park/discard here.)
6. **Ship** via `TASKS ship <id> --shipped "<what actually shipped> (unattended, <model-id>)"` (ends at `--status draft --pr <url>`). The shipped record is required — result, not plan; see flows/implement.md step 6. **An unattended run ships to `draft` and never promotes**: the PR waits there for a human to review and `TASKS ready`. Running `ready` (or `unready`) is a disposal decision, and this run makes none. The draft is the owner's like any of theirs: it shows in the owner's review inbox only (flows/review.md), and once readied the usual rule holds — someone other than the assignee reviews it, the integrator excepted. When the product versions, pass `--version-intent` (or the line in `--body`) per flows/implement.md — the script does not default it. If the change is major/breaking, do not ship — flag `needs: decision` like other forks. Then stop and summarize what was shipped, proposed, or flagged (this lands wherever the invoking automation routes reports). If something shipped to `draft`, add one line: review it via `/dev review <id>`, which is where a human readies it.

## `/dev next unattended` — select one

**Due recurring work comes first** — `TASKS recur list --due`. A recurring task is a candidate only while it is due and eligible on the same terms as any other candidate: `backlog` or `planned`, unassigned or `<owner>`'s, no `needs` flag. One that is not due is never a candidate, here or in the backlog select below. Nothing due → move on; never file a recurring task or offer a cadence.

- **An audit** (a recurring task naming an audit pass — `flows/audit.md` files them as `Recurring audit: <scope>`) **is** the whole run. Read its body for scope and emphasis, take it with `TASKS update <id> --status doing --assignee <owner> --unattended <model-id>` — that is the mutex, since an audit has no branch to claim, and the marker tells the owner it is this run's (refused while any run's marker is set: leave it and select again) — then follow `flows/audit.md`. It edits no files, so area collisions do not gate it. Findings stay `proposed`; the run never approves its own findings nor implements one, and skips audit.md's *Scheduling* offer. Close with `TASKS recur ran <id>` (re-arms to `backlog`, clears the assignee and the marker), report one line per filed task, and stop — no ship, no PR. Interrupted before the stamp, the task stays `doing` for a human: never stamp a pass that did not finish.
- **Any other due recurring task** runs the normal path above — claim, implement, ship. `land` re-arms it rather than marking it done.

Otherwise, candidates are SKILL.md *Next*'s, in its order (`backlog` or `planned`, unassigned or `<owner>`'s — `<owner>`'s own `planned` tasks first — no `needs` flag, all deps `done`, not an umbrella, not ops), minus *Nobody there* above, minus any task on an **attended** routine (`TASKS routine show <name>`: its trigger reaches a person, and taking it here would run it with nobody there). File the untagged fork for each otherwise-eligible untagged candidate, then continue among tagged ones. If nothing suitable exists, report that and stop.

An unattended routine's wake (`flows/wake.md`) runs each task `TASKS routine wake` lists, in order, as `/dev <id> unattended` — a recurring audit through the audit bullet above.

## Report

Each run ends with its summary (step 6, or an audit's lines). When any run in the session flagged `needs: decision` and the harness can notify, the summaries also go to the owner as one notification for the session, never one per run.
