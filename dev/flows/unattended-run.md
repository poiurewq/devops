# Unattended — how a dev task runs with nobody there

The dev part of `shared/flows/unattended.md`, which holds the mode — identity, provenance, the marker, the hard limits, `next unattended`'s candidates, the report and its one notification; read that first. One run = at most one shipped implementation (plus any proposals filed along the way), or one due recurring audit in its place — an audit files proposals and ships nothing.

An unattended run does not go through the lead (`flows/lead.md`): nobody is there to stand in for, and it has no reviewer pass. It follows `flows/implement.md` with the overrides below and stops at `draft`. The marker is set by `claim --unattended` (an audit: `update --unattended`, below).

## Nobody there: what a dev run never takes

These apply to a named id as much as to one `/dev next unattended` selects. A named task they exclude is reported and left alone (an untagged one gets its fork filed, below); `next unattended` skips it and selects again.

- **A `type: ops` task** — it is run, not built: a named one continues as `/ops run <id> unattended` (SKILL.md *Two task types*, crossing over); `next unattended` skips it. There is no branch to claim (`claim` refuses one).
- **Area grounds** (`TASKS collisions <id>` / SKILL.md *Area stewardship*): exit 2 **or 3** → skip, surface the output (any assignee's `doing`, `draft`, or `review`, including the owner's other work). Exit 3 (every blocker's PR already out) offers interactive implement a proceed/stack/wait choice — that is a human call, so an unattended run skips it like any other collision and never stacks. Never pass several candidates as one collisions set — that would treat them as batch peers. Never an `all` task (those wait for a human-supervised quiet board).
- **Untagged**: do not claim and do not invent a placeholder. Recommend a reuse from `TASKS area list` or a new name to `area set`, write the fork (options + recommendation) into the body, and flag `needs: decision` — do not `area set` or `--area` until a human decides (`/dev decide`). **Area sanity**: a mis-tag (replace with same-width or narrower) — fix it and note why (`TASKS update <id> --area "<better>" --append "<why>"`). Adding coverage is the leaving-areas fork: do not `--area` or `area set`; write the file(s) and recommended area(s) into the body, flag `needs: decision`, move on.
- **Fork risk**: read the task body and skim the code it touches; prefer tasks that are mechanical or fully pinned down (clear scope, `Decision:` lines already present, established patterns). Don't force a risky task.

`next unattended` files the untagged fork for each otherwise-eligible untagged candidate, then continues among tagged ones.

## The run

1. **Gate**: `TASKS whoami` must print `<owner>` (`shared/flows/unattended.md` *Identity*), else stop and report. Then `TASKS preflight` (check only — never `--park` / `--discard`). An `error:` (gh not signed in, among others): exit reporting it verbatim. Exit 2 (in-scope ahead): **stop** — report the script output and that a human must park-as-PR or discard via interactive implement; do not claim a task. Exit 0 with out-of-scope-only ahead → soft note in the report, continue.
2. **The task**: the named id, or what `/dev next unattended` selects. Check it against *Nobody there* above. A due recurring audit goes to *Audits* below instead.
3. **Claim**: `TASKS claim <id> --assignee <owner> --unattended <model-id>`. Ship to draft clears the marker; a park hands it back (step 5). If the script errors (e.g. a concurrent claim race on board push), resync; under `next unattended`, select again. Use the printed `product` dir (workdir is the git worktree root).
4. **Triage scope** (flows/implement.md step 1, including its one-layer-at-a-time rule — mid-sized subtasks are fine): if oversized, file the subtasks as proposals rather than adding them live — check `TASKS related "<title>"` first and skip ones the board already has, then `TASKS add ... --status proposed`, each body noting "decomposes T<id>: <why>". Then convert the original into an umbrella and un-claim it: `TASKS update <id> --kind umbrella --deps <new-ids> --status backlog --assignee "" --branch "" --append "Decomposed into proposed T<ids>;"`. Under `next unattended`, return to selection (at most once per run); a named id stops here.
5. **Implement** per flows/implement.md steps 3–6, with one difference — **parking**, the dev run's first stop. At something only a person can settle, do not pick: park the run. `TASKS pause <id> --at "<where it stopped>" --record "<what is on the branch so far>"` commits and pushes the branch, since only ship and pause push and the runner may not outlive the run; then `TASKS update <id> --needs decision --unattended "" --append "Question: <the question, the options, your recommendation> (unattended, <model-id>)"`, and stop (under `next unattended`, return to selection). The task stays `doing` with its branch and holds its area locks until someone answers; `/dev decide <id>` answers it and `/dev <id>` resumes it attended, on any machine — never unattended. What parks:
   - **A genuine design fork** — choices repo conventions already settle don't count.
   - **A flow step nobody can do**: a `[user]` or `[confirm]` step, a checkpoint, or an outward or hard-to-undo step implement would gate (flows/implement.md *Following a flow*) — park at that step, naming what the person has to do or the `About to:` block they say `go` to.
   - **Leaving the stated areas** (flows/implement.md): do not `--area` or `area set`, and do not write those files; the question names the file(s) and recommended area(s). A `Decision:` already on the body for this widen is prior approval — retry apply+collisions; do not park a second time.
   - **An `[external]` step** waits instead: `TASKS wait <id> --on "<who>" --by <date> --at "<step>" --record "<what was sent, and where>"` (it pushes the branch too), then `TASKS update <id> --unattended ""`. No date given → park the question of when, never invent one.

   (Local-ahead was already cleared or soft-noted in step 1 — do not re-triage park/discard here.)
6. **Ship** via `TASKS ship <id> --shipped "<what actually shipped> (unattended, <model-id>)"` (ends at `--status draft --pr <url>`). The shipped record is required — result, not plan; see flows/implement.md step 6. **An unattended run ships to `draft` and never promotes**: the PR waits there for a human to review and `TASKS ready`. The draft is the owner's like any of theirs: it shows in the owner's review inbox only (flows/review.md), and once readied the usual rule holds — someone other than the assignee reviews it, the integrator excepted. When the product versions, pass `--version-intent` (or the line in `--body`) per flows/implement.md — the script does not default it. If the change is major/breaking, do not ship — park it like other forks (step 5). Then stop and summarize what was shipped, proposed, or flagged. If something shipped to `draft`, add one line: review it via `/dev review <id>`, which is where a human readies it.

## Audits

Due recurring work comes first in `next unattended` (`shared/flows/unattended.md`). **An audit** (a recurring task naming an audit pass — `flows/audit.md` files them as `Recurring audit: <scope>`) **is** the whole run. Read its body for scope and emphasis, take it with `TASKS update <id> --status doing --assignee <owner> --unattended <model-id>` — that is the mutex, since an audit has no branch to claim (refused while any run's marker is set: leave it and select again) — then follow `flows/audit.md`. It edits no files, so area collisions do not gate it. Findings stay `proposed`; the run never approves its own findings nor implements one, and skips audit.md's *Scheduling* offer. Close with `TASKS recur ran <id>` (re-arms to `backlog`, clears the assignee and the marker), report one line per filed task, and stop — no ship, no PR. Interrupted before the stamp, the task stays `doing` for a human: never stamp a pass that did not finish.

Any other due recurring task runs *The run* above; `land` re-arms it rather than marking it done.
