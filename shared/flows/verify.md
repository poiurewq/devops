# Umbrella: the verification pass

`/<skill>` is the skill in use. `/dev <id>` and `/ops run <id>` both route a `kind: umbrella` task here, whatever its type: an umbrella carries no work of its own, so this pass checks whether its children actually accomplished its aim (SKILL.md *Umbrella close*). **Nothing is claimed, built or run** — no branch or worktree, no PR, no review, no `Ran:` record — so no area, collision or preflight check either: nothing is edited, so there is nothing to lock or park. Anyone may run it, not only the integrator — usually whoever filed the umbrella and knows what it meant. An unattended run never runs it.

1. **Expand.** `TASKS show <id>` for the goal: its last `Intent:` line (none → get one first, SKILL.md *Intent*) and the details its description lists. Then its `deps` — the direct children. A child that is itself an umbrella is its own pass first; don't verify a parent through an unverified child.
2. **Read the outcomes, not the titles.** Each child is judged by its own record: `Shipped (<date>): …` for a dev child, `Ran (<date>): …` for an ops child, `Verified (<date>): …` for a nested umbrella (closed ones live in `.tasks/archive/…` and `log.md`). Where a record doesn't settle whether the goal really holds, look at the work itself — the code, or what the run left behind — reading without changing anything.
3. **Judge against the Intent, then the description.** Does the union of what the children did deliver what the `Intent:` line asks for — the user's outcome, not the children's titles? Then check each detail the description lists; one left unmet is a gap too. Where a detail and the Intent pull apart (the goal moved past it, or it no longer serves the goal), the Intent wins — but name the mismatch to the user rather than dropping the detail silently. Name any gap concretely. If some children are still open, say which and stop — the pass is premature unless the user judges the remaining ones unnecessary (then they are set aside first, with reasons: SKILL.md *Not planned and shelved*).

Then end it, in this same session, one of two ways. Show the user the judgment — the children you'd file, or the record you'd write — and wait for their go-ahead. Filing new children and closing an umbrella are both human calls (SKILL.md *Ground rules*, humans decide), and this pass is the only gate they get.

- **Gaps** → on approval, file them as new children through the `/<skill> add` path (`shared/flows/add.md`), then attach: `TASKS update <umbrella> --deps <existing+new>`. The umbrella stays open; report what is left. Work the umbrella needs is a **new child**, never work done on the umbrella itself.
- **Goal met** → `TASKS verify <id> "<how the children met the goal>"`, which records it and closes the task. `update --status done` is refused on an umbrella and points here.
