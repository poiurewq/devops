# /<skill> iteration — show, close, start the next

`/<skill>` is the skill in use. Either skill may close a board holding both task types, so every case below is written for any board.

An iteration is one stretch of work on the board plus the archive it leaves behind. A board that never closes is perfectly fine — closing is for when the live board holds more finished work than current work.

**Closing loses nothing.** Every task file is copied verbatim into `.tasks/archive/<n>-<slug>/NNN.md` (`<n>` alone when unnamed) — the full record, greppable and browsable long after the iteration, so `TASKS flow runs <name>` keeps finding past runs. Point people at the archive, never at git history of a deleted file. Flows are not touched: they outlive iterations.

**Numbering.** `iteration` in `board.yml` is a positive integer (1 at init; `init --iteration N` to match a team already in progress), `iteration_name` an optional display label, `iteration_started` a `YYYY-MM-DD` stamped at init and iteration-new (today unless given). Task ids restart each iteration, so a task from an earlier one is written `<n>/T<id>`, as `log.md` lines already are. Archive dirs clash on the number, not the slug. Close writes `started:` / `closed:` lines under `## <n>` (or `## <n> — <name>`) in `log.md`.

## Show

`TASKS iteration`: scope, number, display name, start date, branch, parent, and done/in-play (shelved left out of the done count).

`TASKS config iteration <n>` renumbers the live iteration (refused if that number already has an archive); `config iteration_name` / `config iteration_started` adjust the label and start date. All three are refused once the iteration is closed but not yet rolled or landed, since the close wrote that number into `log.md`.

## Close

1. **Confirm intent, and deal with what is unfinished.** Ask per task: finish it, **shelve** it (`--status shelved --reason "<why>"` — not this iteration, or not needed for now), **carry it over** (it moves into the next iteration with its status, assignee, branch, PR and record intact, a run or a draft in flight included; only its id changes), or **drop** it (`--status not-planned --reason "<why>"`, or delete — the user picks). Dropped and shelved tasks don't block the close. Recurring tasks at rest (`backlog`/`planned`) don't block either and carry over on their own, clock and last run intact; a run in flight (`doing`, `draft`, `review`) blocks like any other task — finish it or carry it, since leaving it behind loses the record of what was done — and so does a `proposed` one, which stays `proposed` when reseeded. An unfinished umbrella means its goal was not met, so moving it off this iteration is a deliberate call, and one whose children are all done needs its verification pass first (SKILL.md *Umbrella close*).
2. **Distill.** Once every unfinished task has its route, run a distill sitting (`shared/routes/distill.md`) — after step 1, since a task finished or dropped there needs distilling too. Build and land the `AGENTS.md` task it files (`/dev <id>`), or carry it over with the rest. `iteration-close` refuses while any `done` or `not-planned` task is in no `Distilled` line, naming them. Only when the user asks to close without distilling: `TASKS iteration-close --skip-distill "<their why>"`, for this close only, logged in `log.md`.
3. `TASKS iteration-close`. When the user chose to carry the unfinished tasks over, add `--carry`: carry is all-or-nothing, so finish, shelve, or drop the ones that should not come along first. There is no closing past unfinished work: every task leaves through one of the routes in step 1, so none is left behind with its branch and PR orphaned. The close archives every task and indexes them in `.tasks/log.md` — one line per task with area, PR, and `[not planned]` / `[shelved]` / `[carried: …]` flags, each task's outcome records (`Shipped`, `Verified`, `Ran`) under it — then clears the live board.
4. **Start the next one** straight away (below), unless the user wants to leave the board empty for a while. A board with a parent branch lands first (*A board with a parent branch*).

## Start the next (in place)

Most boards keep every iteration on one branch and roll in place: `TASKS iteration-new [--name <name>] [--iteration N] [--iteration-started <date>]`, no branch (`--iteration N` is refused if that number already has an archive). Ask for a display name first; unnamed is allowed, but a name is what makes the archive readable later. The script refuses until the close has run (empty board + `log.md` close section), and refuses a branch without `--parent`.

The new board starts empty except for what carries over on its own — do not walk it. Everything that comes back is renumbered 1..N in old-id order, with a `carried from <n>/T<id>` note: tasks closed with `--carry` (status, assignee, branch, PR and record intact), shelved tasks (still shelved), and recurring tasks (armed; a shelved one stays shelved). A recurring task that was not `--carry`'d comes back without its per-run records (Ran, Shipped, Note, Paused, Waiting, `Inputs:`) or its older `carried from` notes; a shelved one keeps its records, since it may hold a paused run to resume, and loses only the old notes. The dropped records stay in the archive, and run history still lists them. Deps and `Dev-batch:` lines among the tasks that came back are remapped; links to tasks that did not come back are dropped. A task left behind that turns out to be needed is new work: `/<skill> add <task-or-goal>`.

## A board with a parent branch

A board with a `parent_branch` keeps each iteration on its own branch and merges it into the parent when it closes; `TASKS iteration` shows whether this board has one.

1. `TASKS iteration-close`, exactly as above.
2. `TASKS iteration-land` — opens the pull request from the iteration branch into the parent if needed, then merges it with a **merge commit**, never squash, so task-level history survives in the parent. It requires a closed board (no live task files, a `log.md` close section for this iteration), and is idempotent: run again after a merge, it says so rather than opening a second one. Nobody has to review it — the diff is the archive the close just wrote — but if the team gates the parent, `--create-only` opens the pull request and stops so a person (typically the integrator) merges it. The agent harness may refuse it, since it merges: that is not a script error — surface it, say the land never ran, and stop; the fix is allowing the command wherever the harness configures permissions (`shared/routes/init.md` *Prerequisites*), never a merge by hand (`gh pr …`, `gh api`).
3. `TASKS iteration-new <branch> [--parent p] [--name n] [--iteration N] [--iteration-started D]` — refused while the current integration branch is not yet contained in the parent, since the new board starts from the parent and would otherwise lack this iteration's archive and `log.md` close section; land it first, there is no override. It starts a fresh board on the new branch and commits a pointer to the `board.yml` of both the parent and the old branch, so a checkout left on either resolves to the new iteration (with a warning to switch); on a push-protected branch that push warns, and checkouts on it then need a one-time `TASKS init --integration <branch>`. The number defaults to one more than the highest live or archived one; `--iteration N` sets it, refused if that number already has an archive. It reseeds as above; carried tasks' worktrees are found by branch (their PR titles keep the old `[n/T<id>]` prefix), and their open PRs on the old branch are retargeted to the new one (a failed retarget warns with the command to run).
4. Tell the user to switch their checkout: `git checkout <branch>`.

Setting a board up this way is `TASKS config parent_branch <branch>`, and it is a real commitment — every future iteration ends in a pull request. Do not propose a parent unasked.
