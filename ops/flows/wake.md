# /ops wake <routine> — a routine's run

The prompt a routine's trigger carries at its source is this one command and nothing else. Every rule the run follows lives here, in the skill and on the board, so changing how scheduled runs behave never means editing a trigger. Run from the product directory, or pass `--scope`.

1. **Skill check.** `SKILL_CMD check` (SKILL.md *Skill check*): show any line it prints, never stop on it.
2. **Gate.** `TASKS whoami` — an error (no readable login, or one not on the roster) stops the run; report it verbatim, since joining a board is a human step. Then `TASKS routine wake <routine>`. Exit 2 → report its reason and stop: nothing runs, and step 5 is skipped (on a one-time routine, add that the trigger is now spent and needs moving at its source once the routine is back). Otherwise `TASKS routine show <routine>` for its mode and schedule.
3. **Run its due tasks**, in the order the wake printed them. The `skipped, waiting on a decision:` and `skipped, in flight:` lines are reported, not started: a decision is the user's to give (`/ops decide <id>`), and an in-flight run — a parked or waiting one included — is someone's to finish. The one exception is on an unattended routine, below.
   - **Attended** (the routine holds one task): `/ops run <id>` as *A scheduled run* (`flows/run.md`).
   - **Unattended**: first, each in-flight task whose parked question now has an answer resumes as `flows/unattended.md` *Resuming a parked run* says, oldest first, as `/ops next unattended` would — otherwise nothing on the routine ever carries it on. Then each due task as `/ops run <id> unattended` (`flows/unattended.md`), one after another in this session. Each is its own run: a task that file leaves alone, parks or sets waiting is reported and the next one runs.
   - **A harness refusal** — a call refused, or held at a permission prompt — is noted where it happens: `TASKS note <id> --at "<step>" "harness refused <call>"`. The post-run tweak fixes it (`flows/run.md` section 6).
4. **Provenance.** Every record the run writes — the `Ran` record, a parked `Question:` — ends `(<mode>, <model-id>, routine <routine>)`, e.g. `(unattended, claude-opus-5-5, routine nightly)`. The unattended `(unattended, <model-id>)` is its prefix, and a run no routine started carries no tail.
5. **Re-point a one-time trigger.** Only when the routine's schedule is one fire time (a timestamp): the trigger is spent once it fires, so the routine fires again only if this run moves it. Do it on every wake that passed the gate, whatever ran, a wake with nothing due included.
   - **When**: the earliest next due among the routine's tasks (`TASKS recur list`; `ran` prints a closed run's). A task not re-armed — still in flight (parked or waiting) or waiting on a decision — counts as if it ran now: its cadence from today, or its schedule's next time after now.
   - **Move it** at its source when the harness lets this session (the routine's body says how), then mirror it on the board: `TASKS routine update <routine> --schedule <timestamp>`. Never the board alone — it mirrors the source.
   - **Cannot** → notify the user with the time to set and the routine's body, and leave the board's schedule as it is. The not-started warning only shows once that time has passed, too late to save a spent trigger.
6. **Report.** One line per task (what its run reports), the skipped lines, the re-point (moved to when, or the user notified), and any harness refusal noted. The notification rules of the flow each task ran under hold: an unattended session sends one notification at most, and an attended run has already reached the user if it needed them.
